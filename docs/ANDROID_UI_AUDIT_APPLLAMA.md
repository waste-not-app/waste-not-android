# Audit UI Android WasteNot dengan Appllama

Baseline audit: `0bd21b8`, setelah [polish liquid glass #139](https://github.com/waste-not-app/waste-not-android/pull/139). [CI baseline](https://github.com/waste-not-app/waste-not-android/actions/runs/44488798028) lulus; hasil itu tidak membuktikan alur di HP. [Render host dan screenshot sebelumnya](archive/qa/iteration-2/LIQUID_GLASS_AUDIT.md) dipakai sebagai pembanding historis, bukan render commit ini. Implementasi memakai `main` terbaru saat pekerjaan dimulai, [`cbcf563`](https://github.com/waste-not-app/waste-not-android/commit/cbcf563), dengan resource EN dan ID.

**Kerjakan alur scan sampai simpan dulu.** Tombol untuk meneruskan saran yang valid sudah ada di kode. Masalah yang terlihat dari susunannya: pengguna harus melewati isi saran dan bisa melewati daftar sumber yang panjang sebelum sampai ke aksi. Bertambahnya efek kaca tidak menyelesaikan masalah itu.

## Urutan implementasi

1. **Scan dan editor (A01–A02).** Buat render baseline pada commit ini untuk saran valid dan bersyarat, lalu perbaiki satu alur sampai konfirmasi simpan. Lulus jika tindakan berikutnya mudah ditemukan pada 320 dp/font 200%, syarat tidak bisa dilewati, jumlah tetap harus diisi, dan satu konfirmasi menghasilkan maksimal satu catatan. Uji prototipe/expired/unavailable secara terpisah. Tidak mengubah aturan saran, API, atribusi foto, atau XP.
2. **Feedback dan pemulihan (A03, A04, A06).** Benahi simpan pengingat yang prematur, query Panduan, tautan, dan expansion. Lulus jika kegagalan bisa direproduksi melalui hasil terkontrol di host, sukses hanya muncul setelah operasi selesai, dan input tetap ada setelah gagal. Pertahankan separator, sumber yang valid, dan paginasi yang sudah ada.
3. **Chrome dan konsistensi visual (A05, A07).** Buat tujuan dock/rail mudah ditemukan dan seragamkan peran shape, label, fokus, serta kontras. Pertahankan urutan lima tab, aksi Scan di tengah, dan maksimal dua permukaan blur. Periksa Beranda, setiap tab, dialog, dan form bersama; jangan mengganti fitur yang sudah memenuhi tujuan layarnya.
4. **Penerimaan.** Bandingkan sebelum/sesudah di host pada 320 dp/font 200%, 390 dp/font normal, 600 dp/rail, terang/gelap, dan viewport pendek. Target sentuh ≥48 dp, teks normal ≥4,5:1, batas/fokus yang membawa informasi ≥3:1. Periksa loading, kosong, error, offline dan state panjang. Jalankan tes yang mencakup perubahan, lint/build dan CI pada branch implementasi.

**Gerbang HP fisik.** Setelah pemilik menyambungkan HP dan meminta uji, rekam alur login → scan → saran → editor → simpan → Riwayat, termasuk Back/IME, TalkBack, izin kamera, swipe sheet, tiga tombol/gesture, Reduce Motion dan offline. Uji API 30 untuk fallback dan API 31+ untuk Haze bila perangkat tersedia. Bandingkan frame timing build release untuk scroll/transition yang sama sebelum dan sesudah; target 60 fps pada perangkat referensi, bukan klaim audit ini. Tidak memakai emulator. Jika MCP diotorisasi, mulai dengan `get_credits`, lalu perluas benchmark per alur yang akan diubah; jangan menganggap 11 still publik ini pengganti riset motion atau perbandingan lengkap.

## Polish warna, saran, dan motion

Mengikuti hierarki Juno dari benchmark di atas: lime paling kuat untuk **Catat/Scan**; tab terpilih memakai tint yang lebih tenang. Header dan dock tetap satu-satunya permukaan blur, dengan tint botani dan bayangan lebih ringan. Fallback opak memakai keluarga warna yang sama; kartu isi tetap solid.

Saran menampilkan satu metode dengan aksi **Ubah**. Pilihan yang diubah diberi label sebagai pilihan pengguna, bukan saran baru. Peringatan dan syarat wajib tetap di luar rincian; membuka rincian tidak memindahkan posisi tombol lanjut. Pergantian langkah memakai fade 150 ms; rincian dan chevron bergerak singkat mengikuti pengaturan animasi Android. Alur simpan dan perhitungan XP tidak berubah.

**Verifikasi:** 34 tes host lulus, termasuk kontras dan dock pada 320 dp. Di itel API 33, 14 skenario berbeda lulus: 11 tes sheet scan, dua perjalanan Panduan terang/gelap, dan satu tes rail landscape. Dua skenario scan diulang pada skala animasi 0; pengaturan ponsel dikembalikan. Screenshot kedua tema, tampilan rail, dan frame pergantian langkah diperiksa dari build QA. Ini bukan pengukuran frame timing release atau uji fallback pada perangkat API 30. Tanpa AVD; benchmark Appllama tetap memakai referensi publik karena endpoint MCP meminta autentikasi.
